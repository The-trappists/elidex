| 2026-11-07 | Evaluation matches an extracted item with an expected one on (type, scope, action similarity) instead of the topic slug; the model comparison script `scripts/eval_models.py` reports matched, missed, unexpected, binding differences and link precision and recall (see [evaluation.md](evaluation.md)) | Keep matching on (type, topic) | Two models name the same knowledge differently (`sfp-swap-first-step` vs another slug) but should bind to the same things and advise the same action; the slug measured naming luck, not extraction quality | UnPtitBelge (with Claude) |
| 2026-11-07 | Models by role: extractor on Gemini via AI Studio with Featherless as fallback; critic and judge on a DIFFERENT provider (Mistral recommended, Groq as critic fallback) so that errors are not correlated. Every provider is smoke-tested by a human before the team relies on it; agents never use the `.env` keys. Free-offer findings and their sources are in [tech-stack.md](tech-stack.md#model-roles-and-free-access); several of them are unverified | One model for every role; OpenAI (no event credits, ChatGPT Plus does not include API usage); OpenRouter free models (20 requests per minute, 50 per day without credit); Cerebras trial ($5, too tight) | A reviewer from the same model family tends to repeat the extractor's mistakes; the event credit ($25 Featherless) and the free tiers cover the small volume of a demo; the final choice must come from the numbers of `scripts/eval_models.py`, not from guesses | UnPtitBelge (with Claude) |
| 2026-11-07 | The loop is fully automated: knowledge goes live with no human review, and no specialist is ever asked for a click, a confirmation or a rating. The operator console ("Needs a look", assertion editor, item re-run) is optional, for observation, debugging and manual override, and never a gate. Its UI/UX quality is a first-class goal. Each new behaviour sits behind a `Settings` toggle (`use_critic`, `use_judge`, `use_outcome_loop`, default on; critic and judge stay silent without an LLM key) | A review inbox where an operator confirms knowledge before it is live; asking technicians to rate the agent's advice | Elisa's brief says specialists must do no extra work; a review queue would be the same extra work moved to someone else. Flags stay informational, and an operator override is recorded as source `operator` and can be undone | UnPtitBelge (with Claude) |
| 2026-11-07 | Linking stays deterministic (`link.py`: exact IDs, aliases, class from type, model and install years, abstain when unsure). LLM agents sit only where the text is ambiguous. A vague scope word ("old") is kept as `Scope.qualifier` and lowers the confidence of the class by x0.8 instead of becoming a precise class | Let an LLM bind entities; embedding similarity for linking | "A wrong link is worse than none": a deterministic linker can be tested and explained, and a model that guesses an element id would spread a rule to the wrong equipment | UnPtitBelge (with Claude) |
| 2026-11-07 | Keep the pipeline (listen, understand, link, store, reconcile) and add three targeted agents: a critic inside understand (second model checks each item against its quote), a reconcile judge after store (supports, contradicts, supersedes, unrelated against neighbours) and a passive outcome loop (the agent's applied action is posted in a thread, the technician's reply updates trust). No full multi-agent orchestrator. Implemented on branch `worktree-loop-v2`, see [plan-loop-v2.md](plan-loop-v2.md) | A full multi-agent orchestrator (for example Google ADK); better prompts only, with no extra agent | The pipeline is small and works; the three agents target the weak spots (over-wide scope, topic-slug reconcile, trust that never changes) while keeping the stages testable and every agent switchable off. An orchestrator would cost most of the 48 h for no visible gain; prompts alone cannot add a second opinion or a feedback signal | UnPtitBelge (with Claude) |
| 2026-11-07 | Workbench UI refactor: calm, flat design (neutral surfaces, one accent, color only for status), one job per screen (Overview, Conversations with a step-by-step pipeline view, Network, Graph, Knowledge), and a new Graph page that shows the knowledge graph from `GET /api/graph`.
